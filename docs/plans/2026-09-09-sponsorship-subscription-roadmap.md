# 贊助管理與月卡升級 Roadmap

- 建立日期：2026-09-09
- 狀態：路線圖已建立；**階段 0 規則與 V1 規格已確認**。階段 1 前後端皆已有部分實作；2026-09-12 已取得授權執行隔離測試 DB 並取得 129 tests 全綠的真實 DB 整合測試證據（見 §4「2026-09-12 驗證結果」小節），但**仍未完成完整驗收**——全 CI、完整真實瀏覽器寫入流程與正式上線 gate 仍是明確待辦，**不可視為階段 1 完成**。詳見 §4 進度記錄與驗證缺口。
- 目標：讓站務不必進機器發月卡，能追查玩家現金貢獻，再逐步提升月卡價值。
- 順序：**規則確認 → 贊助／發卡後台 → 月卡福利與價格調整 → 選擇性金流自動化**。
- 本文件記錄方向、依賴與驗收門檻，不代表已核准未定價格、福利額度或正式環境操作。

## 1. 背景與現有系統

現金 donate 由站務人工確認後，進機器發行月卡序號；玩家也能用女神石購卡。希望新增管理介面，一次處理贊助登記、發卡與玩家貢獻查詢。

已查到的程式依據：

| --- | --- |
| CLI 發卡 | `app/bin/IssueSubscribeCard.js` 依卡種與數量產生序號；尚無現金明細。機器端是否另有包裝指令待確認。 |

`app/seeds/SubscribeCardSeeder.js` 是初始化資料，不能當作正式售價、線上福利或既有資料升級程序。

## 2. 共同原則

- 第一版由站務（僅本人，非全部 admin）確認收款後人工登記，不串金流、不在登記時直接啟用訂閱。
- 保留序號交付與兌換；贊助者、操作管理員、實際兌換者分開記錄，允許送卡。
- 現金貢獻只計已登記金額；遊戲幣購卡不算現金，不以卡數反推金額。V1 無退款能力，故只顯示「累積登記贊助金額」，不顯示淨貢獻或任何淨額；日後若要支援退款，須先補上退款能力才能正確算淨額。
- 支援純贊助不發卡／發卡兩種；歷史補登不得再次發卡，也不猜測缺漏金額，且不與舊序號建立關聯。
- 資料提交後不可修改（僅例外：歷史紀錄事後補綁玩家）；V1 不提供一般更正、刪除、序號作廢，也不提供退款。
- 現金金額僅限授權本人查看，不出現在公開群組或排行榜；玩家自查暫緩。
- 保留既有訂閱及未兌換序號承諾；正式資料操作與部署另行確認。

前端已有 mock 版瀏覽器操作紀錄，涵蓋：新增贊助（純贊助／發卡兩分支）、歷史補綁、非本人/未登入被拒絕跳轉、未知結果碼落在同一個 key 顯示、逾時重試沿用同一 `request_id`（不產生新請求）、頁面重新整理後不自動重送。**這些是 mock 後端下的瀏覽器行為驗證，不是對真實後端的 e2e 測試**，不能取代 §12 要求的「本人登入可見並操作完整流程」人工驗收。

前端 `yarn build` 目前無法在本機驗證通過；已排除「lock 檔缺少 wordcloud 依賴」的假設——探勘確認 `wordcloud` 確實同時存在於 `frontend/package.json` 與 `frontend/yarn.lock`，真正原因是本機 `node_modules` 缺這個套件且既有安裝與 lock 檔的 integrity 不吻合。修復需要重新安裝依賴，本輪使用者要求「先不要變更環境」，**未經授權不安裝**；正常 build 驗證因此暫停，留待使用者授權後再執行。

真實 MySQL 整合測試檔（§11 表列的 `SponsorshipService.integration.test.js`、`SubscribeController.redeem.test.js`）**尚未建立、亦未執行**，以下項目目前完全沒有可重現的證據，不能假稱已驗證正確：

- 交易回滾三情境（發卡中途失敗、audit(create) 失敗、audit(bind) 失敗後的殘留檢查）。
- 補綁併發下不重複 audit；`unique(request_id)` 併發只成功一筆。
- 兌換併發五情境（雙玩家搶同序號、同玩家雙序號各種既有/首次建立分支、過期清理後重兌）。
- `SUM(amount)` 以 DB decimal 實際加總正確（目前只有 mock 回傳值的斷言）。
- `received_at` 的 DATETIME 入庫與 `+08:00` 連線時區設定（`app/src/util/mysql.js`）之間的實際 round-trip：目前程式是直接把 normalize 後的 **UTC ISO 字串**丟給 knex 寫入 `datetime` 欄位，是否與既有 `+08:00` session timezone 設定正確對應、讀回後是否還原成同一個時間點，**尚未經真實 DB 驗證，不能假稱已經處理正確**，需要專門的 round-trip 測試修正並確認。
- migration 本身未在真實/隔離 DB 上跑過驗證。

`SPONSORSHIP_OWNER_LINE_USER_ID` 尚未提供真實值，授權中介層目前僅能在假 ID 下測試；正式啟用前仍需使用者提供並設定該值。

**本輪使用者明確表示暫不允許安裝依賴或啟動隔離測試 DB**；本文件依指示只記錄上述驗證缺口與暫停原因，不讀取 `.env`、不觸碰 `Princess` 或既有 infra。**下一步待使用者允許環境變更（安裝依賴/啟動隔離測試 DB），或提供一個安全的本機測試 DB 後，補齊 §11 整合測試、跑通前端正常 build、完成真實 e2e 人工驗收，階段 1 才能視為完成**。在此之前，不把目前的單元測試與 mock 版瀏覽器操作勾成「全部驗收通過」，也不自稱贊助後台功能已完成。階段 2（福利/價格）與階段 3（金流）依然不在本輪範圍內。

### 1A：先完成一條端到端流程

> 本人登入 → 搜尋並辨認玩家 → 填寫實收款 → 選卡種／張數或純贊助 → 確認（明示送出後不可修改）→ 複製序號 → 玩家兌換 → 查詢結果。

- [ ] 建立贊助明細、序號關聯與必要操作紀錄（`sponsorship` + `sponsorship_audit`）；付款人不因送卡而改變。
- [ ] 實作後端授權（僅本人 `SPONSORSHIP_OWNER_LINE_USER_ID`，非全部 admin）、輸入驗證及玩家搜尋，避免同名誤認；新贊助必綁既有玩家，不得用 `ensureUser` 自動建號。
- [ ] 登記、發卡、必要操作紀錄在同一交易內完成，失敗不能留下半套成功資料。
- [ ] 防止連點、逾時重試及同一次操作重複登記（Idempotency-Key + `request_id`）；重送同一次操作取得原結果，內容不同回 409。
- [ ] 管理介面支援確認、成功／失敗提示與查回原序號，不以重新發卡代替交付重試。
- [ ] 修正既有序號兌換的交易外讀取風險，確保不會因重複或併發請求多給權益（同序號多玩家搶兌、同玩家多序號並發皆須交易內行鎖 + 有限重試）。

### 1B：補齊查詢與歷史補綁

- [ ] 贊助列表：玩家（可能未綁定）、入帳日期、金額、類型（新贊助/歷史）、關聯序號及兌換結果。
- [ ] 玩家詳細頁：累積登記贊助金額（TWD）與贊助歷史；**不顯示**退款合計或淨貢獻（V1 無此能力）。
- [ ] 歷史補登：只依可核對資料記錄未綁定紀錄；補綁只能由未綁定變已綁定，已綁定不得換人；不新增序號、不與舊序號建立關聯。
- [ ] 確認 CLI 與後台切換方式，避免同一筆贊助兩邊各發一次；CLI 與購卡路徑改走共用發卡服務，價格與既有參數不變。

**V1 明確不做（非待決，不在本階段範圍內）：**退款、一般更正、刪除紀錄、序號作廢、歷史與舊序號關聯、任何淨額／退款合計欄位、跨表單重複偵測。

### 驗收與上線門檻

- [ ] 非本人使用者（含其他 admin）直接呼叫 `/api/owner/sponsorships/*` 任一端點（含查詢）皆被拒絕。
- [ ] 發卡失敗完整回滾；重送不重複入帳或發卡；純贊助不發序號。
- [ ] A 贊助、B 兌換：現金貢獻留在 A，訂閱只給 B；發卡本身不啟用月卡。
- [ ] 遊戲幣購卡不增加登記贊助金額；歷史補登不發卡；已提交資料不可修改（僅歷史補綁例外）。
- [ ] 舊序號、既有訂閱及 CLI 的約定流程仍可使用，回歸測試綠燈。

## 5. 階段 2：月卡福利升級與價格調整

**依賴：**階段 1 驗收完成，發卡與現金紀錄可追查。

- [ ] 由授權人員核對現行卡種、福利、售價及存量，不從 seed 推定正式設定。
- [ ] 選定首波福利；候選為自動化升級、補簽容錯、可永久收藏的外觀，並非全部承諾實作。
- [ ] 確認額度、週期、到期與續卡行為，以及送卡時外觀／回饋屬於誰。
- [ ] 確認現金與遊戲幣取得同一卡種的待遇；建議福利一致，尚待決定。
- [ ] 確認舊有效訂閱、未兌換序號與續卡的過渡規則，避免改卡種設定就覆蓋舊承諾。
- [ ] 完成福利實作與驗收後，再確認新價格、生效時間及公告。

**完成門檻：**新福利與到期行為符合規則；舊承諾保留；現金與遊戲幣價格說明符合實際操作；歷史實收金額不因調價重算。

## 6. 階段 3：選擇性金流自動化

**依賴：**前兩階段穩定，人工對帳負擔足以支持投入；可長期不做。

- [ ] 評估交易量、費用及對帳需求，再選供應商。
- [ ] 付款通知沿用既有贊助／發卡流程，不另建現金貢獻帳本。
- [ ] 加入付款驗證、防重複處理、漏通知對帳、重試與人工補處理。
- [ ] 保留人工營運；退款與直接啟用訂閱不因串金流而默認改變。

**完成門檻：**未付款不發卡；同一付款重送不重複入帳／發卡；漏通知可補處理；金流停用時仍能人工營運。
